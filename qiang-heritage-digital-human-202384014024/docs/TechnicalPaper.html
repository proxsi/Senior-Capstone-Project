Qiang Heritage Digital Human:
A Retrieval-Grounded Conversational System for Intangible Cultural Heritage

Technical implementation report on a Chinese-language, three-tier question-answering application that combines a curated heritage knowledge base, live web search, and a persona-conditioned language model.

Abstract

This paper documents the technical implementation of a question-answering system for Qiang intangible cultural heritage. The system pairs a React single-page client with a FastAPI service and answers visitor questions through a three-tier routing policy: a curated knowledge base of embedded heritage chunks is consulted first, a live web-search model is consulted when the local evidence is weak, and the language model answers from its own parameters only as a last resort. Each answer is returned with its provenance, a confidence value, and a fallback flag, so that the interface can display where the statement came from. The written knowledge is stored as semantic chunks with subject, entity type, topic tag, relation text, and an embedding vector; chunks are produced either by a human curator through a structured form or by a language model that rewrites unstructured text into a JSON array which the operator edits before committing. A digital-human presenter reflects conversation state through pre-rendered video clips, and synthesized speech is streamed back as base64 MP3. The paper describes the actual implementation as submitted, including its storage model, its prompt construction, its provider adapters, and its measured-by-inspection costs, and it states the limitations of the design rather than claiming unverified performance.

Keywords: retrieval-augmented generation; intangible cultural heritage; digital human; FastAPI; vector search; provenance-aware answering

1Introduction

Intangible cultural heritage is transmitted through people: through the explanation a craftsman gives while working, through the stories told during a festival, through the corrections an elder makes when a younger person uses the wrong word. Digitising such knowledge is therefore not only a retrieval problem. A useful heritage assistant must answer accurately, admit when it does not know, and speak in a register that a visitor finds natural rather than administrative.

Large language models satisfy the third requirement easily and the first two poorly. A model asked about a specific Qiang embroidery pattern will produce fluent prose whether or not it has ever seen a reliable description of that pattern. The risk is asymmetric: a visitor cannot tell a confident fabrication from a curated fact unless the interface exposes its evidence. This project was built around that observation. Instead of treating the model as the source of truth, the system treats it as a writer that receives evidence from a curated store or from a live search, and it reports which of those sources was used for every answer.

The scope of the implementation is deliberately narrow and end-to-end. It supports one conversational persona, one heritage domain, one storage schema, and a small set of provider integrations. The contribution documented here is an engineering one: a working, annotated implementation that makes the evidence path explicit, together with an ingestion console that allows a non-programmer to add curated knowledge and inspect what the model extracted before it is stored.

2Design Requirements and Scope

Three requirements drove the design, and each maps to a concrete mechanism in the code.

  • Grounded answers with visible provenance. Every response carries a source_type of local, web, llm, or image, plus a reference string and a fallback_used flag. The client renders this as a badge under the answer instead of hiding the distinction.
  • Curator control over stored knowledge. Bulk text is not written directly to the database. The extraction result is returned to the browser as an editable table, and a second explicit request commits it. This separates "what the model thinks the text says" from "what the institution agrees to publish".
  • Conversational naturalness. A single Chinese system prompt defines a named persona with a regional background, an age, a speaking style, and an explicit list of forbidden phrases such as "as an AI model". Retrieval context is framed as village records or outside news so that the persona can introduce evidence without breaking character.

Out of scope are multi-tenant access control, editorial workflow with approval roles, offline speech recognition, and any quantitative evaluation against a labelled heritage question set. The paper returns to these omissions in Section 10.

3System Architecture

The deployment consists of one Python process and one static bundle. FastAPI serves the JSON API, mounts the compiled frontend under /assets, and returns index.html at the root when a production build exists. Because the page and the API share an origin, the client uses window.location.origin as its base URL and no CORS configuration is needed.

A question travels through the system as follows. The client appends the user's bubble, takes a snapshot of the visible history, and posts a JSON body to /chat. The server validates the body with a Pydantic model, and either diverts to image analysis when a base64 attachment is present or calls the retriever. The retriever decides whether the input is casual conversation or a knowledge question, gathers evidence, builds a prompt, and calls the chat provider. The response object carries the answer and its provenance; the server records a counter and returns JSON. The client then requests speech for the answer, reveals the text progressively while the audio loads, and finally commits the message to the transcript.

Two architectural decisions deserve emphasis because they are easy to misread from the module names. First, the online retrieval path uses PostgreSQL only; the Neo4j loader is a separate ingestion path that the retriever never calls. Second, the answer is not token-streamed by the model: /chat returns a complete JSON object, and the apparent typing effect is produced by the client.

4Retrieval and Answer Generation

4.1Conversational pre-routing

Before any database access, the query is tested against curated pattern lists covering greetings, self-introduction, small talk, emotional support, care, praise, and teasing. Inputs shorter than five characters, or greetings shorter than twenty characters, are treated as conversational and answered with a direct persona prompt. A secondary rule catches short mood questions that contain both a mood keyword and a self-reference such as "you" or the persona's name. Each matched family supplies a short instruction that tells the model how to frame the reply, for example to empathise before comforting and not to pivot into a heritage lecture. This stage exists because retrieval for "hello" wastes an embedding call and produces an unnatural answer.

4.2Three-tier evidence selection

Tier 1 · Local knowledge Embed the query; take the five nearest chunks and merge up to five keyword matches; report the top vector similarity.
→
Tier 2 · Web search Used only when the top similarity is below the threshold. Qwen answers with the web_search tool.
→
Tier 3 · Model knowledge Used only when search returns no text. The persona answers without retrieved context and the confidence is reported as 0.1.

The local tier fuses two retrieval signals. Vector neighbours are loaded with a top-five limit, and a keyword query contributes up to five additional rows whose chunk text or subject name contains one of the first three whitespace-separated query terms. Duplicate texts are removed by a set. Vector hits keep their cosine similarity; keyword-only hits receive a fixed score of 0.5 so that a lexical coincidence cannot outrank a strong semantic match. The score reported to the caller is the highest vector similarity, not the fused score, and the routing test compares that value with a configurable threshold:

if smax ≥ τ then local, else if web text non-empty then web, else llm

with τ = 0.75 by default. The similarity itself is the cosine measure

sim(q, d) = (q · d) / (‖q‖ ‖d‖)

computed with NumPy over the stored JSONB vectors. The normalisation matters because chunk lengths vary; without it, longer passages would dominate the ranking.

4.3Context framing and persona

All tiers share one system prompt. It establishes the persona's name, age, home county, and familiarity with embroidery, watchtowers, flutes, and oral tradition; it requires short natural sentences, permits the Qiang greeting "纳吉纳鲁" sparingly, and forbids meta-language about being a model, a database, or a program. It also prescribes an in-character response to uncertainty: the persona says that she would rather ask an elder than invent an answer. This is a deliberate design choice. Refusal phrased as a cultural norm is more consistent with the character than a technical disclaimer, and it preserves the epistemic boundary that the retrieval design is meant to enforce.

Each tier then supplies a different context wrapper. Local evidence is introduced as records kept by the village elders, web evidence as news from beyond the mountains, and the no-evidence case as an ordinary conversation with no framing at all. The last six history turns are inserted before the current question, with the user labelled as a guest and the persona labelled by name. The history is passed as plain role and content pairs; identifiers, timestamps, and image previews are stripped by the client because they carry no meaning for the model.

4.4Provenance in the response model

The chat response is a validated object with six fields: answer, source type, reference, confidence, fallback flag, and timestamp. Confidence is not a calibrated probability. It is the top cosine similarity for the local tier, a fixed 0.5 for web answers, 0.1 for unaided model answers, and 1.0 for image analysis and conversational replies. The interface uses it as a ranking hint and as a colour cue, not as a statistical guarantee. Naming the value honestly is part of the design: presenting an unnormalised similarity as a probability would mislead the reader.

5The Digital-Human Presenter

The presenter is a state machine over pre-rendered clips rather than a lip-synchronised model. Six clips are grouped into four roles: a welcome animation, two idle loops, two thinking clips, and one talking loop. The component keeps both React state and a mutable reference to the current state, because media event handlers are registered once and would otherwise close over a stale value. A useImperativeHandle exposes three commands to the parent: start thinking, start talking for a given duration, and end the conversation.

Table 2. Avatar states and transitions.
StateClip behaviourEntered when
welcomePlays once, then hands over to an idle loopFirst mount
standbyAlternates between two idle clips on each endingWelcome finished, or speech ended
thinkingFirst clip twice, then the second clip in a loopA question is submitted
talkingSingle talking clip stored in a loop-friendly elementSpeech metadata or playback begins

Speech is produced by a separate service. For each answer the client calls POST /tts, receives base64 MP3, decodes it into a Uint8Array, wraps it in a Blob, and plays it through an Audio element created from an object URL. The clip duration is read from loadedmetadata and forwarded to the avatar so that the talking state lasts roughly as long as the voice; when the browser does not report a duration before playback resolves, a twelve-second fallback is used. Terminal handlers revoke the object URL, which prevents blob memory from accumulating across a session.

Two details in this pipeline are worth recording because they shaped the client code. Autoplay of the greeting is frequently blocked by browser policy, so the component keeps a pending flag and retries on the first user gesture while showing a manual replay control. And the answer bubble is committed only after the audio ends, so that the visible text and the spoken text stay in step; if synthesis fails, the text is still shown and the avatar returns to idle.

6Knowledge Ingestion and Curation

6.1Chunk model

Knowledge is stored at the granularity of a semantic chunk rather than a document. A chunk is a short passage about one subject along one dimension, for example the history of a named embroidery style or the region in which a festival is practised. The schema is shown in Table 3.

Table 3. Storage schema of non_heritage_knowledge_chunks.
ColumnTypeRole

entity_typeVARCHAR(50)Project, inheritor, festival, place, craft, other; indexed
topic_tagVARCHAR(50)Definition, history, process, value, works, bearer, region, other; indexed
embedding_textTEXTThe passage that is embedded and shown to the model
relation_descTEXTFree-text relations, parsed by the graph view

embeddingJSONBVector serialized as JSON text
created_at, updated_atTIMESTAMPInsert and last-write times

6.2Browsing the curated store

Stored chunks can be listed with pagination and filtered on the client. The list shows the subject, entity type, topic tag, relation description, and source link, which is enough for a curator to spot duplicates or malformed entries without direct database access.

6.3Structured single-entry upload

The simplest ingestion path asks the curator for every field explicitly. Nothing is inferred. The embedding text is sent to the embedding provider, and the returned vector is written with the metadata in a single upsert. The identifier combines a timestamp with a process-local counter, and the insert uses ON CONFLICT (chunk_id) DO UPDATE, so re-ingesting the same identifier updates a row instead of raising an error.

6.4Model-assisted bulk extraction

Bulk text follows a two-phase protocol. In the preview phase the raw text is placed in a prompt that fixes the output contract: a JSON array whose objects contain subject, entity type, topic tag, embedding text, relation description, and source URL, with the entity and topic vocabularies restated. The model is asked to write the embedding text as a self-contained passage that begins with the subject name and the topic dimension. Temperature is lowered to 0.3 for this call because the task is extraction, not conversation.

The return value is not trusted blindly. Because the model may wrap the array in prose, the processor isolates the outermost bracketed block with a regular expression before parsing, and a parse failure produces an empty list rather than an exception. The parsed objects are returned to the browser, where the curator can edit or delete rows. Only an explicit confirmation request embeds and stores them. Persistence is per chunk: a failure on one row is logged and the remaining rows are still attempted, and the response reports the saved count against the submitted count.

6.5The optional graph loader

A second loader targets Neo4j. It splits text with a 500-character window and a 50-character overlap, and it backs the window boundary up to the nearest sentence-ending punctuation when one is found within the last hundred characters. Entities are extracted with regular-expression rules for bearers, projects, and Sichuan place names, then written as Inheritor, HeritageProject, and Location nodes with INHERITS edges. Chunk embeddings are stored in a cosine vector index of dimension 768. This path is not used by the online retriever; it exists for deployments that want a graph-native store and a queryNodes search instead of the PostgreSQL path.

7Knowledge-Graph Visualisation

The graph view is derived on the client from the chunk list rather than from a dedicated graph endpoint. Each chunk contributes a typed node keyed by its subject name; a relation description containing a related project name contributes an edge. Colour encodes entity type and radius encodes degree, so a subject that appears in many relations is visually prominent. Node and edge collections are deduplicated with maps, which keeps the simulation stable when the same subject appears in several chunks.

When a chat answer mentions one of the known heritage entities, the parent component stores it and the graph re-centres on the matching node, which links the conversation and the structural view. If the chunk request fails, the component falls back to a small illustrative graph so that the panel never renders empty. The fallback is clearly a demonstration, not stored knowledge, and the code labels it as such.

8Multimodal Question Answering

An attached image is read in the browser, converted to a data URL, and posted as a base64 payload with its MIME type. The presence of that field is the switch: the server bypasses retrieval entirely and sends a multimodal message to the configured vision model. The user's text becomes the instruction, and a dedicated system prompt asks the persona to describe the image honestly, to connect it to Qiang culture only when the connection is real, and to state plainly when a detail is uncertain.

This path is intentionally not retrieval-grounded. A photograph of an object is not a query against the chunk store, and pretending otherwise would produce misleading provenance. The response therefore reports source_type = image with confidence 1.0, and the interface displays it as a distinct category. The trade-off is that image answers are only as reliable as the vision model, which is precisely why they are labelled differently.

Request and response bodies are declared as Pydantic models with field descriptions, which gives the service a typed contract and a generated OpenAPI page at /docs. Two stores coexist: the SQL chunk table used by retrieval, and a JSON file used by the simple knowledge list endpoints. The duplication is a historical artefact and is disclosed rather than hidden.

9.2Provider adapters

Each external provider is isolated behind a small adapter that owns throttling, retries, response parsing, and error normalisation. The chat and embedding clients share a class-level timestamp so that the minimum interval applies across instances rather than per object. The chat client accepts a tools argument for interface compatibility but discards it; tool calling is not implemented in this adapter. The search client uses the provider's web_search tool in the request payload, and any non-200 response is converted into an empty result so that the routing logic can fall through to the next tier without exception handling at the call site.

9.3Frontend composition

The client is a React 19 application built with Vite 7 and styled with Tailwind. State that is shared between panels lives in the root component: the entity mentioned in the latest answer, the visibility of the knowledge console, and an imperative handle to the avatar. The chat component owns its transcript, attachment state, audio element, and loading ticker. The API layer is a single axios instance with a 180-second timeout, which accommodates a language-model call followed by a web search in the same request.

The transcript uses React Markdown for answer rendering, an auto-scroll sentinel for pinning the newest message, and a set of refs to keep media callbacks idempotent: a flag prevents onAudioStart from firing twice for the same clip, a ref guards the greeting against double seeding under React's strict-mode mount cycle, and a pending flag records a blocked autoplay so the first gesture can retry it.

9.4Configuration and credential handling

All provider keys, database settings, thresholds, and server options are read from environment variables with defaults in config.py. The coursework package contains an English .env.example with placeholders only; the working .env used during development is excluded. Knowledge of a deployment's database host or password is not required to read, build, or assess the code, which is the point of separating configuration from implementation.

10Discussion

10.1What the design buys

The strongest property of the implementation is that evidence and answer are separated in the response contract. Because the tier is explicit, a curator can inspect the counter endpoint and see how often the system answered from stored knowledge, and a reader can see on screen whether a statement came from the institution or from a live search. This is more useful than a single opaque answer, even though it does not by itself guarantee correctness.

The two-phase bulk ingestion protocol is the second useful property. Extraction by a language model is unreliable in ways that are hard to predict, and a human review step turns an all-or-nothing import into a supervised one. The per-chunk write policy means a single bad row does not discard an entire batch.

10.2Costs visible by inspection

Several costs follow directly from the code and can be stated without a benchmark. Vector search loads every embedded row into the application and ranks it in Python, so query cost grows linearly with table size and the database does no index-assisted vector filtering. Keyword search interpolates user terms into a LIKE clause with an f-string, which is acceptable only under the supervised, single-tenant conditions of this coursework and would need bound parameters in any exposed deployment. The chat request is blocking from the client's point of view, with a three-minute ceiling; a slow model plus a slow search can therefore hold a request open for most of that window. Statistics are process-local and reset on restart. No route has authentication, and the write routes for knowledge are as open as the read routes.

10.3Threats to validity

No labelled question set was constructed, so this paper makes no accuracy claim. The threshold of 0.75 is a configuration default, not a tuned operating point; whether it is appropriate for embedding-3 on Chinese heritage text would require measurement. The confidence field is a similarity or a constant, not a calibrated probability. The graph view derives structure from free-text relations with a regular expression, so its edges are a presentation aid rather than a verified ontology. Finally, the screenshots document one running deployment on one dataset; they demonstrate that the interface works, not that the knowledge base is complete.

The honest conclusion is that the system is a well-structured prototype with explicit provenance, a supervised ingestion path, and a clear boundary between what is retrieved and what is generated. It is not an evaluated heritage expert.

11Conclusion and Future Work

This paper described a complete question-answering application for Qiang intangible cultural heritage, implemented as a FastAPI service and a React client with an annotated codebase. The system routes each question through a curated knowledge base, a web-search fallback, and a final model-only tier, and it reports which tier answered. Knowledge is stored as semantic chunks with subject, type, topic, relation, and embedding fields; ingestion supports both structured manual entry and model-assisted extraction with mandatory human confirmation. A digital-human presenter and synthesized speech carry the conversational state, and a client-derived graph exposes the structure of the stored knowledge.

Four directions follow naturally from the limitations. Moving similarity search into the database with a vector index would remove the linear scan. Introducing a labelled evaluation set of heritage questions would allow the threshold to be tuned and the fallback rate to be reported. Adding parameter binding to the keyword query and an authentication layer to the write routes would make the service safe to expose. Replacing the presentation graph with a curated ontology would turn the visualisation into a queryable structure rather than a derived sketch.
